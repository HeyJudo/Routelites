1. SYSTEM DESIGN AND METHODOLOGY
  1. System Architecture Overview

RouteLite is a routing decision-support system for small local businesses that handle their own deliveries within a fixed service area. It accepts a selected store location and several delivery stops, checks whether those inputs are valid, prepares them for road-network computation, and then generates both a naive and an optimized closed route. The architecture brings together user input, shortest-path computation, and route optimization in a workflow suited to small-scale local delivery planning.

The architecture is divided into three main stages. The first is input and validation, where the selected store and delivery stops are checked to confirm that they are inside the service area, reachable in the prepared road graph, not duplicated, and still within the allowed stop limit. The second is routing preparation, where valid locations are matched to their nearest road nodes and processed using Dijkstra's Algorithm to compute pairwise shortest-path distances. The third is route optimization and result generation, where RouteLite first computes the naive closed route based on the user-input order, then applies Branch and Bound for the Travelling Salesman Problem to find the optimal closed tour and compare the results. This structure allows the project to handle both road-level path computation and stop-sequence optimization in a clear and connected way.

  1. Input and Validation Process

The input and validation stage is the starting point of the workflow. Here, the user selects one store or dispatch point, and several delivery stops from the prepared local dataset within the fixed service area. These selected locations form the routing request, which RouteLite checks before any computation begins. This prevents the project from processing incomplete, invalid, or unreachable inputs.

  1. Routing Preparation Process

Once the inputs pass validation, the workflow moves to routing preparation. This stage converts the selected locations into data that can be used for road-network computation. Because the chosen places are stored as location points rather than direct graph nodes, each one is first snapped to its nearest road node in the preprocessed OpenStreetMap-based road graph.

After the selected places have been matched to road nodes, RouteLite runs Dijkstra's Algorithm from each selected node to compute the shortest-path distance to every other selected node. These results are used to build the distance matrix, which becomes the input to the optimization stage, and they also preserve path data that can later be used for route display. At this point, the validated place selections have already been converted into the road-based representation needed for Branch and Bound in the next stage.

  1. Route Optimization Process

Once the distance matrix is ready, RouteLite moves to route optimization. It first computes the naive closed route based on the order in which the user entered the delivery stops. This acts as the baseline for comparison and reflects the common manual practice of following requests in input order.

RouteLite then applies the Branch and Bound method for the Travelling Salesman Problem to find the optimal closed tour. Using the distance matrix as input, the algorithm searches for the best order of stops that starts at the selected store, visits each delivery point once, and returns to the same starting point. The optimized route is then compared with the naive route to determine which one has the shorter total travel distance.

  1. Output and Result Presentation

Once route optimization is complete, RouteLite presents the results to the user. The output includes the optimized stop sequence, the naive route based on input order, the total distance of each route, and the distance saved through optimization. This allows the user to see whether the optimized route is more efficient than the original delivery order.

It may also display the actual road path for each leg of the route using the path data preserved during the Dijkstra stage. This helps the user understand not only the stop order but also the road-based path followed between locations. The final output therefore connects the optimization result to a route that can be interpreted more clearly in actual delivery planning.

  1. Methodology for Algorithm Implementation

RouteLite uses two main algorithms: Dijkstra's Algorithm for shortest-path computation and Branch and Bound for route optimization. Dijkstra's algorithm is applied during routing preparation after the selected places have been matched to their nearest road nodes. For each selected node, the algorithm initializes the distance values, sets the source node distance to zero, and repeatedly picks the unvisited node with the smallest tentative distance. It then checks the adjacent edges of that node and updates the distance and predecessor values whenever it finds a shorter path. One run produces the shortest-path distances and path information from one selected node to the others. Running the same process for all selected nodes allows RouteLite to build the distance matrix needed for route optimization.  Check the flowchart presented below.

Image 2. Dijkstra’s Algorithm Flowchart

Branch and Bound is applied after the distance matrix has been formed. In RouteLite, each partial route is treated as a state, with the algorithm tracking the current path, the remaining unvisited stops, and the current route cost. It first checks whether all stops have already been visited. If they have, the tour is closed by returning to the starting store, and the full route cost is compared with the best solution found so far. If the route is still incomplete, the algorithm computes a lower bound for the current state. When that bound is already greater than or equal to the best recorded cost, the branch is pruned. Otherwise, the algorithm continues by exploring the next possible stops and recursively evaluating only the states that still appear promising. This allows RouteLite to avoid checking every possible route and focus instead on the strongest candidates. See the flowchart below for the flow of Branch and Bound.

  1. Pseudocode

The pseudocode below summarizes the main logic of RouteLite and the two algorithms used in the system. It is presented after the methodology section so that the flow of the implementation can be seen in a more structured form.

Overall RouteLite Pseudocode:

BEGIN RouteLite
   LOAD road graph and local place dataset
   GET store and delivery stop inputs
   IF inputs are invalid THEN
       SHOW error message
       REQUEST revised input
       STOP current process
   END IF
   SNAP selected places to nearest road nodes
   FOR each selected node
       RUN Dijkstra from the current node
       STORE shortest distances and path data
   END FOR
   BUILD distance matrix from shortest-path results
   COMPUTE naive route based on input order
   RUN Branch and Bound TSP using the distance matrix
   COMPARE naive route and optimized route
   DISPLAY route order, total distance, and distance saved
END RouteLite

        Dijkstra's Algorithm pseudocode:

DIJKSTRA(Graph, Source)
   FOR each node v in Graph
               dist[v] = INF
             prev[v] = null
               visited[v] = false
  END FOR

   dist[Source] = 0
WHILE there is an unvisited reachable node
       u = unvisited node with smallest dist[u]
       visited[u] = true
       FOR each neighbor v of u
           alt = dist[u] + weight(u, v)
           IF alt < dist[v] THEN
                       dist[v] = alt
                       prev[v] = u
           END IF
     END FOR
END WHILE
   RETURN dist, prev
END

Branch and Bound TSP pseudocode:

BRANCH_AND_BOUND_TSP(Matrix, Start)
   bestCost = INF
   bestRoute = null

   CREATE initial state:
       path = [Start]
       currentCost = 0
       unvisited = all stops except Start

   SEARCH(path, unvisited, currentCost)

   RETURN bestRoute, bestCost
END

SEARCH(path, unvisited, currentCost)
   IF unvisited is empty THEN
       fullCost = currentCost + return-to-start cost
       IF fullCost < bestCost THEN
           bestCost = fullCost
           bestRoute = completed path
       END IF
       RETURN
   END IF

   COMPUTE lowerBound for current state
   IF lowerBound >= bestCost THEN
       RETURN
   END IF

   ORDER candidate stops by increasing edge cost

   FOR each candidate stop
       nextCost = currentCost + edge cost to candidate
       IF nextCost < bestCost THEN
           CREATE child state with updated path and unvisited set
           SEARCH(child path, child unvisited, nextCost)
       END IF
   END FOR
END

  1. Output

After the user selects the store and delivery stops, RouteLite generates an output that explains the recommended delivery route and the basis of the result. The main output is the optimized delivery sequence, which shows the order in which the delivery unit should visit the selected stops before returning to the store. This sequence is produced using the shortest-path distances computed by Dijkstra's Algorithm and the route order determined through Branch and Bound.

The system also displays the naive input-order route, which represents the route that follows the original order in which the user entered the delivery stops. This is shown beside or below the optimized route so the user can compare the difference between manual planning and algorithm-based routing.

For each route, RouteLite presents the total estimated distance. It also shows the estimated distance saved by subtracting the optimized route distance from the naive route distance. This allows the user to understand the practical benefit of using the optimized route, especially in terms of reduced travel distance.

When available, the system may also show the road-level path for each route segment. For example, it can display the path from the store to the first stop, from one stop to the next, and from the final stop back to the store. This makes the result more understandable because the user can see not only the stop order but also the road path used for each part of the route.

For larger delivery sets, the output may indicate if the route was processed using batch-based optimization. In this case, RouteLite shows the complete route plan that covers all selected stops, while also identifying the optimized batches used by the system. This helps clarify that the route remains practical and organized even when the number of selected delivery stops is large.

The final output of RouteLite includes the following:

  • Optimized delivery sequence.
  • Naive input-order route.
  • Total distance of the optimized route.
  • Total distance of the naive route.
  • Estimated distance saved.
  • Road-level path per route segment, when available.
  • Batch grouping information, when batch-based optimization is used.
